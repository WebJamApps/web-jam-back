# backup rules



- **Active Export In-Progress Run Guard & Reservation**: Single-run in-progress guards that inspect remote storage (such as Dropbox folder listings) miss in-flight operations (like database export) before the first upload occurs. Acquire an in-process run guard/reservation before starting export, hold it throughout export and upload, and fail competing parallel or sequential starts closed. Always release the guard in a `finally` block so failed exports do not lock out future runs.


- **HTTP Endpoint Prerequisite Refusal**: When background operations require specific environment settings or credentials, the HTTP route handler must validate prerequisite settings synchronously before accepting the job and returning 202, returning a clear failure status (e.g. 500) rather than accepting the job and failing silently in the background.


- **Distinguishing Missing Entities from Lookup Errors in Remote Storage**: When checking whether an entity (manifest, file, folder) exists via an external API (like Dropbox 409 Conflict), never treat all error responses as "not found". Inspect the error body to positively identify `path/not_found`. Treat other lookup errors (such as `restricted_content`) as hard errors so uncertain folders are never deleted during retention pruning.


- **Distinguishing Run Refusals from Operational Run Failures in Scheduled Tasks**: When orchestrating scheduled background jobs or health checks (such as hourly backup sweeps), never treat start refusals (e.g. competing runs in progress, locked state, or cooldowns) as job failures (`lastRunFailed = true` or firing failure alerts). A refusal to start means the system prevented duplicate execution, not that a running job broke or that data was lost. Schedulers must catch in-progress / start-refusal exceptions separately: suppress failure emails, preserve the previously recorded run outcome (do not flip `lastRunFailed` to `true`), and leave status reporting reflecting verified historical runs.


- **Decoupling Single-Role Route Guards from Multi-Role Infrastructure (`AUTH_ROLES`)**: When an issue specifies that a route or router is gated exclusively on an authoritative role (e.g. `Developer`) independently of `AUTH_ROLES` (including when `AUTH_ROLES` is unset or configured without that role), guard middleware must NOT delegate token verification to `authUtils.ensureAuthenticated()`. `ensureAuthenticated` ends in `findUserById()`, which validates caller roles against `AUTH_ROLES[route]` and refuses callers when the route key lacks the role. Guards must decode the JWT token payload directly and verify the caller's account via `user-schema.ts`. Router test suites must verify that authorized callers are served and unauthorized callers are refused when `AUTH_ROLES` is unset or explicitly excludes the role.


- **Asset & Static File Path Resolution Across Source (`src/`) vs Compiled (`build/`) Layouts**: When reading non-code files (such as documentation, templates, diagrams, or assets like `docs/system-map.mmd` or `src/model/template/assets`) from disk at runtime, never rely solely on relative paths from `import.meta.dirname` (e.g. `../../../docs/...`) that are only exercised against the TypeScript `src/` layout during unit tests. In production (Heroku `Procfile`, `npm start`), Node runs compiled JavaScript from `build/src/...` (`node build/src/index.js`), which introduces an additional directory level (resolving to `build/docs/...` instead of the repo root). Always ensure: (1) paths resolve via `process.cwd()` (the application root on Heroku dynos and local dev) or candidate fallback chains that support both `src/` and `build/` layouts; (2) packaging scripts (`scripts/copy-assets.mjs`) copy non-TypeScript assets to `build/` if referenced under `build/`; (3) unit/integration test suites explicitly assert that path resolution resolves to an existing file when simulated from the compiled directory layout (`build/src/...`), not only the `src/` layout; and (4) never introduce ad-hoc, test-only environment variables (such as `SYSTEM_MAP_PATH`) into production code to force error branches in tests; pass optional path arguments or use test spies (`vi.spyOn(fs.promises, 'readFile')`) instead.


- **Strict "No Address" Verification in System Maps & Diagram Specifications**: When architecture documentation or diagrams enforce a rule of "service names and connections only, never an address, a login or a secret", "address" strictly includes hostnames and domain names (e.g. `web-jam.com`), not just IP addresses or URL schemes (`https?://`). Labels must strictly name services (e.g. `Website`) rather than network addresses. Test suites enforcing the rule must include regex patterns that reject domain names and hostnames (e.g. `/\b[a-zA-Z0-9-]+\.(com|org|net|io|edu|gov|dev|invalid)\b/i`).


- **Recursive Embedded Schema Traversal in Database & Architecture Diagrams**: When generating database diagrams, Mermaid ER representations, or model relationship graphs from Mongoose schemas, never inspect only the parent model's top-level `schema.paths`. In Mongoose, embedded document sub-schemas and document arrays (`instance: 'Embedded'`, `instance: 'Array'`, `instance: 'DocumentArray'`) do not expose their nested attributes directly on the parent schema paths; they store their paths in `schemaType.schema` or `schemaType.caster?.schema`. Diagram generators must recursively traverse embedded schemas at every depth, tracking ancestor schemas to prevent cycles, and emit all sanitized nested field paths (e.g. `items_songId`, `touches_outreachId`, `touches_targetWeekend_start`) along with their types and unique flags. All reference targets (`ref`) must be discovered recursively at all depths so generated relationship definitions (`Entity }o--|| Target : path_field`) always match attributes present in their corresponding entity blocks. Parameterize schema traversal helpers with minimal structural types (`SchemaLike { paths: Record<string, unknown> }`) rather than bare `mongoose.Schema`, which drags in incompatible Mongoose internal virtual/query-helper generics (`TS2345: virtuals unknown is not assignable to {}`) between model schema instances. Unit tests verifying generated diagrams must independently assert nested field presence inside specific entity blocks rather than only repeating a shallow top-level `schema.paths` traversal.
